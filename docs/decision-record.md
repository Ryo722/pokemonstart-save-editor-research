M1 / Gate 1 is complete on `main`. The merged read-only verifier has no write path, its synthetic tests pass, and the supplied private original/test/resave set reproduced the expected slot selection, section validation, party decoding, footer separation, and sectors 30/31 diagnostics without changing the input files.

The current branch is an authorized **M2 bounded one-field writer proof candidate**. It adds `pokemonstart_hpiv_proof_writer.py` plus synthetic tests and documentation only. The writer is deliberately pinned to the exact known before-test save SHA-256 `fcbdef7ac3e629ec3884def5df1894f108a267f639692791796bb5389783fe0b` and one transformation: party slot 0 HP IV 31 -> 30. It refuses every other input hash, refuses input overwrite and existing output paths, requires the complete byte diff to be exactly `0x10080 BF->BE` plus `0x10FF6 62->61`, and requires output SHA-256 `569fc5b2b18c77593a0f55bbe01fd20a603fe96ce9c5f955b978710d117db0dc`.

Private local preflight generated that exact output from the supplied before-test save. The source hash remained unchanged, the output was byte-identical to the retained earlier HP-IV-30 proof save, and the M1 verifier accepted the generated bytes with the expected invariants. This closes the repository-implementation/diff-reproduction uncertainty, but not the human round-trip gate.

## Final goal

Enable a PokemonStart player to inspect and make a small, explicitly chosen party edit to their own save, verify it, and recover the original if anything fails. A Windows GUI is a delivery option only after the file format and individual field writes have evidence. The current proof does not justify treating untested fields or other PokemonStart builds as safe.

## Fresh roadmap re-evaluation

No new evidence justifies changing the North Star or skipping the one-field round trip. The current M2 step remains the cheapest and safest uncertainty reducer because the byte-level transformation is now deterministic and bounded; the only material uncertainty left inside M2 is whether the exact repository-generated file survives a fresh real game load/resave cycle.

The fact that the repository output is byte-identical to the retained historical HP-IV-30 proof substantially reduces implementation uncertainty, but it does not justify silently substituting historical gameplay evidence for the explicit current M2 gate. A fresh round trip is cheap, reversible, and directly tests the integration boundary that static verification cannot prove.

## M2 design decision

The M2 writer is intentionally narrower than a reusable writer library:

- input is allowlisted by exact SHA-256;
- only party record 0 is targeted;
- only HP IV 31 -> 30 is accepted;
- the active slot and logical section 1 are discovered through the M1 verifier rather than assumed from physical position;
- section 1 checksum is recalculated after the one field change;
- the complete output diff and output SHA-256 are fixed expectations;
- footer, sectors 30/31, party count, active slot, and all non-HP IVs are invariant checks;
- output is created with exclusive new-file semantics and any post-write verification failure removes the newly created output;
- the input is re-hashed after writing and must remain unchanged.

This design is intentionally non-general. Its benefit is that any unexpected behavior becomes a hard failure rather than an inferred save edit. The trade-off is that it cannot edit any other save or even the same save after a normal game resave. That is acceptable for M2 because the milestone is a proof, not a user-facing editor.

## Authorization and risks

The current authorization covers this bounded M2 implementation, synthetic tests, private local generation of the one proof output, branch documentation, and preparation of a reviewable candidate. It does **not** authorize merging the candidate into canonical `main`, generalizing the writer to other hashes, adding editable fields, overwriting saves, GUI work, box editing, protected-data publication, executing Defender-blocked executables, or broadening distribution scope.

Known technical risks remain: PokemonStart version/build mismatch; inability to prove title identity from structural save layout alone; future variants with different signatures/layouts; emulator-footer semantics beyond opaque preservation; field coupling; expanded IDs; checksum/write ordering; interrupted-save behavior; and the fact that one successful HP-IV proof cannot establish safety for other fields.

The next meaningful human gate is the **fresh M2 game round trip** using the repository-generated private output. After a successful load and normal in-game save, the new resave should be supplied privately for read-only verification. Only then should M2 completion and candidate merge be considered.
